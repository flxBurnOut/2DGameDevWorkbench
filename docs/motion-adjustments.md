# 用户选帧修改与备选版本

“调整部分帧”用于对开放动作作品做明确修改，也接受个人偏好；不要求专家先判定原动画有错。只读查看、选帧和填写要求不创建任务。用户点击“生成一个备选”或授权 Agent 提交后，才保存独立修改任务并使用额度。

新修改继承来源工作冻结的复核版本（当前新工作为可见性核对版本 4），旧工作不随服务更新升级。目标改善与未要求内容的退化分别判断；最终复核与独立专家的具体矛盾未解决时保留待人工确认；用户已否定的作品仍是失败。见[视觉结构](visual-structures.md)与[视觉复核](sprite-review-evaluation.md)。

## 使用流程

1. 在分段确认或“检查与调整”中点击“调整部分帧”，进入专注的调整区；“返回动画检查”回到原片段。进入后收起原播放与采用工具，避免两套操作并列。当前帧的局部编辑可从播放器直接进入。
2. 选帧并填写“修改要求”。填写时以用户原话建立修改目标，专家建议不能覆盖它；留空时使用当前范围的专家建议；两者都没有时需补充想尝试的变化。修改要求与专家意见分别留存。
3. 提交前显示理解、绘图和复核上限：一次任务最多一次需求理解、一次 PixelLab 请求，以及两次基础复核或至多五次增强复核（无争议可少一次）。模型设置在提交时冻结，凭据仍从保护存储读取。
4. 生成方式默认按原帧和文字要求推荐，也可显式选择受限外观编辑或动作重画；与所选范围不兼容时拒绝。未要求变化的姿势、外观、时机应保留。
5. 可选勾选“精确限定修改区域”显示画笔，逐帧涂选后由本地合成保护区域外 RGBA。未勾选时没有空间硬锁定，须看实际对比。
6. 备选生成后，同页同步播放原版与备选，逐帧观察完整片段及两侧衔接。界面分别显示“修改目标”和“其他内容保持”，不能用目标改善抵消新退化；区域模式还显示区域外像素核验结果（只证明保护区没变，不证明改动好看）。
7. 用户实际播放并填写简短结论、确认需接受的提醒后采用。保留原版不会删除备选、未知请求或已产生的费用。

只有真实备选存在时才显示对比和采用选择；理解失败的记录标注“未生成备选”。已完成的备选自动呈现，旧结果在“修改记录”中查看。完整候选有未处理备选时，刷新返回检查页；保留原版后可继续导出。恢复入口只在存在待恢复的绘图请求时出现。

编号约定：需求理解使用与页面一致、从 1 开始的原帧编号；绘图提示只描述所选局部窗口，不把完整动画编号当作绘图输入槽位。视觉观察先读备选，后续审查、独立专家与争议复核同时看到受保护的原版作对照，这些对照复用原有调用，不增加复核次数。

## 保证与边界

**范围保护**

- 范围绑定作品版本、候选、真实帧哈希、参考图、FPS、循环和计划。所有模式下，未选中帧逐张保持原文件字节，不改帧序、帧数或 FPS。
- 起始帧、完整候选中已锁定的分段锚点和停留帧始终受保护。当前未确认片段若后段尚未提交、末帧未绑定原图或外部目标图，末帧可以纳入用户的明确选择，界面标为“未锁定段尾”；采用并确认本段后，新的真实末帧才成为后段输入。
- 用户要求改变保护范围、整体时长等时，意图理解应说明冲突并停止绘图。当前范围没有合适方案时，不假装完成修改。

**区域模式**

- 区域只能来自用户明确授权，不能把结构蒙版或时序观察当作空间许可，也不能把一帧的坐标套到另一姿势。勾选后每个选中帧必须有非空、非全图的有效区域；切换来源后旧区域失效。
- 区域外 RGBA 逐像素不变，区域内的效果与接缝仍须判断。未传 `edit_regions` 是正常的时间窗口编辑路径，不能声称帧内像素锁定。
- PixelLab 没有空间蒙版接口：它收到原帧和有边界说明的提示，原始返回完整保留，交付结果用二值区域合成。区域内透明部分允许删除碎片。范围过窄可能留下接缝；模型若移动了整个物体，合成也不保证选区内合理。系统不会扩大区域或自动再次生成。

**帧数限制**

- 128 像素外观编辑一次 2 个目标帧；64 像素支持 2–14 个偶数帧；运动过渡支持 4–16 个偶数帧。模型输入中的参考 / 上下文图片不进入替换结果。
- 单帧、奇数帧或不支持的范围在付费调用前拒绝，不扩大选择、补帧、删帧，也不偷偷切换生成方法或拆成多次收费请求。例如 128 像素第 13–16 帧要求保留动作时直接拒绝。只有明确修改动作的需求才适合评估 4–16 帧的过渡生成。
- 未锁定段尾的外观编辑以受保护的前一帧作额外上下文；过渡生成从该前一帧开始，不把有缺陷的旧末帧当作固定目标。只接纳提供方返回的所选数量。过渡生成可能改变所选帧的姿势，不能承诺只改局部像素。

**采用与覆盖**

- 当前未锁定片段采用后绑定新帧和已完成的备选报告，仍需明确确认该片段。完整候选采用后建立同一作品的新版本和新原生作业，原版本、原候选与导出保留。
- 完整性评价以本次要求为准：用户要求覆盖冲突的专家建议，后续明确采用的局部修改按顺序覆盖更早的同范围要求。最终整段检查仍保留。

## 费用、失败与恢复

每个修改任务分别保存规划、绘图、视觉调用的请求身份、输入摘要、模型、响应和用量。`work.adjustment_usage` 汇总该作品历次修改的调用次数。原生任务预算与修改预算分别核算，不重复扣除，弃用后也不清零。

**绘图次数按帧计。** 每帧在当前版本、候选和片段（或完整候选）中最多参与两次修改绘图：

- 13–14 帧的尝试不占 15–16 帧的次数；部分重叠的选择取所选帧中最少的剩余次数，不能移动边界绕过已用完的帧。采用后也不清零。
- 未进入绘图的理解失败或需求冲突不占绘图次数，但规划费用和失败记录保留；已提交、失败或结果未知的绘图都计数。
- 旧局部修复只占其实际涉及帧的次数，原有任务总预算和接口限制不变。
- 上下文返回 `attempt_scope=selected_frames`、`attempt_limit=2`、逐帧的 `frame_attempts` 和 `legacy_frame_attempts`。Agent 应读取当前选择覆盖的计数，不要用 `tasks.length` 推断额度（任务条数包括理解失败和不同范围的记录）。关联的隔离试做也按真实绘图范围计数。

每次新提交仍需明确授权独立上限；已有待处理或未知的备选会阻止并行新建。重复的请求标识只返回原任务。后台只推进已授权的任务；未知提交或中断的调用保留记录并停止，不自动重新生成。GET、刷新、读历史和查询 MCP 任务不发起新的规划或绘图。原始图片或任务合同变化时，备选保留但不能直接采用到新来源。

**冻结的协议版本**（旧任务缺少相应字段时沿用原合同，不升级）：

- 意图格式 v4：沿用已验证 TokenHub Kimi 的严格 JSON Schema。有明确用户要求时，历史专家建议留在记录中，不作为额外目标送入理解请求。绘图使用一次完整简短的目标翻译，为槽位 / 区域说明预留长度，不重复拼接原话、旧动作或理想收势，不截断。空要求只使用相关的具体建议。
- `spatial_policy=source_pixels_v1`（区域任务）：冻结逐帧来源哈希和稀疏二值区域；Kimi 提示长度按用户原话与保护说明的剩余空间计算，不截断用户要求。
- `comparison_protocol=1`：复用原观察、审查、独立外观 / 动作意见及至多一次争议复核，在相同调用中分别回答 `change` 与 `preservation`。任一项失败不能被另一项抵消；比较项争议也能在原预算内触发第五次复核。取消先前疑点仍需人工画面裁决，缺失或无效结论不算通过。

**错误记录。** HTTP 拒绝只保存状态码、合规错误码、已识别的参数名与提供方请求编号，不保存或展示原始错误正文、图片、提示词或凭据。HTTP 400 不能直接推断为余额不足或图片丢失；历史记录没有具体原因时保持未知，不自动重试或换模型。

**采用校验。** 采用前验证图片与报告的绑定；阶段采用复用同一份检查结果，不重复请求模型。报告费用记在独立任务账本，原生阶段保留来源链接。采用后整段组装的检查是另一个范围，使用原有预算。技术硬错误禁止采用；模型“不确定”不等于通过，需实际画面裁决。

## MCP 输入

均属于 `sprite-generator`，先读取当前 capability schema。

1. `get-motion-adjustment`：带 `openWorkId`、`expectedRevision`、`candidateIndex` 读取上下文。`stageIndex` 指定当前未锁定片段，省略为完整候选。返回 `adjustmentContext`、可修改范围、当前建议、调用上限和校验过的 `orderedFrames`。不提交模型。
2. `create-motion-adjustment`：带同一身份、`adjustmentToken`、零基闭区间 `adjustmentStart/adjustmentEnd`、可选 `adjustmentRequest`（用户原话）、`generationAuthorized=true`、`adjustmentBudget` 和稳定 `requestKey`。
   - 已明确只修外观时传 `adjustmentPreserveMotion=true`，超出原帧编辑容量的范围会被提前拒绝。
   - 只有用户主动选择空间保护时才提供 `adjustmentRegions` 并同时传 true；每项 `{frame, source_sha256, spans:[{start,length}]}` 绑定实际帧哈希，不能猜坐标。不传区域不等于允许无关改动，也不能声称像素锁定。
3. 用 `workbench_get_task` 跟进同一任务，或用带 `adjustmentId` 的 `get-motion-adjustment` 读取已有修改。返回真实原帧和备选帧路径，按完整顺序播放，不以 GIF 首帧代替检查。
4. `review-motion-adjustment`：使用来源 `expectedRevision`、`adjustmentId`、`adjustmentToken=preview_token`、`stageDecision=accept|reject`。采用需实际 `reviewNote` 及必要的 `acknowledgeWarnings`。尚无预览的失败 / 未知请求要保留原版时，使用 `source_token`。

新协议不改变旧 `repair-motion-stage`、旧方案哈希或旧任务执行语义。界面与 MCP 使用同一后台。修改任务归属原作品，不另算一件已完成资产；完整候选只有明确采用后才形成可导出的衍生版本，也不代表已接入游戏工程。

## 确定性帧编辑

图片编辑目标 `motion-frame` 包含 `workId / workRevision / candidateIndex / stageIndex / frameIndex`，省略 stageIndex 表示完整候选。矩形、连通色、Alpha、手工像素等选区先按原图解析，再精确转换为 `FrameEditRegion`，不从结构观察自动取得授权。单帧确定性操作沿用图片工作区；64/128 像素动画不会进入 GPT Image 的大图生成路径。

图片候选的采用动作先保存一个 `local_pixels_v1` 动画备选，此时动画本身尚未变更；完整播放后以该备选的 token 采用。它不涉及规划、绘图或视觉模型调用，局部像素核验不代表视觉通过。单帧和奇数帧都可执行，免费编辑不消耗绘图次数。

多帧色表通过 MCP `edit-motion-frames` 或 HTTP `local-frame-edits` 提交；网页提供单色替换和“选中全部可编辑帧”。每帧须有明确的原始 SHA256 和选区。整图选择只允许用于这条本地路径，PixelLab 受限生成不能用全图选区冒充区域保护。锁定帧不能提交，网页的全范围操作会明确跳过它们。保存后逐帧验证未选区域 RGBA，不改帧数、顺序、FPS 或循环。

采用到未锁定段后仍需确认该段。完整候选采用会派生新版本，跨段映射逐段回写，锁定锚点与停留帧不变。连续编辑派生版本时，继承的原始帧另存到历史证据目录，不占用新版本的不可变播放目录。

任务的 `repair_level` 区分 deterministic、restricted_generation、window_redraw、stage_redraw；stage_redraw 只指覆盖一段全部**可编辑帧**，不允许重画已锁定边界。真实费用保留提供方用量，未返回价格时不推算美元。人工检查时间可单独填写，旧记录缺值保持未知。

## 维护与验收

核心模块位于 `collaboration/`：

| 文件 | 职责 |
| --- | --- |
| `adjustments.py` | 独立任务、冻结范围、预算与执行 |
| `adjustment_regions.py` | 明确区域、本地回填与 RGBA 核验 |
| `adjustment_comparison.py` | 修改目标与保留内容的独立结论 |
| `adjustment_review.py` | 复用检查 |
| `adjustment_delivery.py` | 采用及衍生版本 |
| `adjustment_import.py` | 关联已完成的隔离备选（见下） |

UI 为 `motion-adjustment.tsx` 与按需出现的 `motion-edit-region.tsx`；MCP 清单与 Sprite 适配器共享原生接口。

回归顺序：`tests/test_motion_adjustments.py`、现有开放动作与专家复核测试、`test:open-motion`、隔离浏览器完整流程，再按开发指南运行接口 / MCP / Agent / 壳层回归、类型检查和构建。Skill 更新时运行两份 validator。

真实质量验收需另获额度，记录基线与备选的全部实际帧、范围外哈希、真实调用与弃用结果，分别验证：按用户指定方向修改、采用专家建议、保留满意的原版、备选更差时的退出路径。模拟接口与模型报告都不能证明真实效果提升。

`adjustment_import.register_saved_alternative` 用于本地维护时关联已完成的隔离备选。调用者须指定原作品、版本、候选、片段和来源 token；函数验证冻结输入、原图、全部 PNG、复核证据和请求身份，原子复制并保存关联来源。旧费用仍计入试做上限，无新调用、无采用，也不新增 MCP 操作。不得把不同来源的成功样例关联为当前任务的备选。

### 实测记录（2026-10-27）

三轮实测均为单独授权，结论说明了当前能力边界：

| 轮次 | 范围与调用 | 结果 |
| --- | --- | --- |
| 修复前失败案例 | 128 像素第 13–16 帧，只要求修外观；1 次理解、1 次绘图、5 次复核 | 被帧数限制导向过渡重生成并重新引入规划收势，姿态、轮廓和碎片退化。模型部分通过，用户判定失败，备选已拒绝。由此引入“不切换生成方法”的约束；该回归只证明错误路由被约束，不证明修复质量。 |
| 区域保护 | 第 13–14 帧；1 次理解、1 次 PixelLab、5 次复核，无重试、无采用 | 区域外 RGBA 零改动，其余 14 帧字节不变，十字碎裂与散落亮点减少；但两帧刀刃投影的长度与曲直仍有差异，人工不接受模型“形状一致”的结论。只记工程保护通过和局部改善。 |
| 默认文字路径（不涂选） | 两个隔离副本各一次；合计 2 次理解、2 次编辑、9 次复核 | 拖尾样例（第 8–9 帧）白色拖尾减弱、原运动未被重做，未选帧字节不变；武器样例（第 13–14 帧）清除了十字碎片，但刀刃角度变化及接回第 15 帧的跳变仍在，人工未判通过。前者支持普通原帧编辑的方向，不证明精修普遍可靠。 |

逐帧三列对照与同步播放保存在本地验收目录。最后一轮时完整 Python 测试 639 通过、2 跳过，浏览器与接口回归通过。不得沿用这些轮次的授权追加生成。
