# Forge 使用与操作手册

本手册面向第一次使用 Forge 的创作者、通过 WorkBuddy 协作的使用者，以及接手项目的 Agent 和开发者。内容覆盖本机启动、角色美术、交互物、图片局部调整、素材交付和 Godot 接入，以及备份、排错与验收。

日常使用时，在 WorkBuddy 中描述目标，由 Agent 完成已开放的生产操作，也可以直接在工作台编辑。完成后下载真实素材或 Godot 包，再交给工程 Skill 接入游戏。

本手册对应当前本地集成版本。独立序列帧上游仓库是否有相同功能需另查其提交，本机可用不代表远程已更新。

贯穿全手册的三条规则，后文不再逐处重复：

- **模型报告只是建议。** 规划、视觉复核和结构解析的结论都不会自动修改、重画或采用素材，最终以你看过的实际画面为准。
- **旧作品不随升级改变。** 新规则只用于新建或显式修订的工作；旧任务、旧报告和导出保留原版本，浏览、刷新或恢复不会补做收费检查。
- **结果不明时不重发。** 超时、断连或刷新后，先查询原任务；已提交的付费请求不会自动重试，再次提交沿用同一请求标识，不会重复创建。

## 1 先认识工作台

### 谁负责什么

Forge 网页负责编辑、预览、制作记录和导出。WorkBuddy、Codex 等外部客户端中的 Agent 负责理解需求、选择工具和编写获授权的游戏代码。网页没有另一个通用聊天 Agent。

MCP 是客户端调用工作台工具的接口；Skill 是告诉 Agent 如何完成某类工作的项目说明。连接 MCP 能获得工具，但不能代替宿主读取 Skill、操作内部浏览器或修改目标游戏的权限。

| 入口 | 用途 | 谁来操作 |
| --- | --- | --- |
| 角色美术 | 角色原图、动画候选、检查、修补与导出 | Agent 可调用已开放的 MCP；精细修补在界面完成 |
| 交互物 | 门、开关、查看物件、拾取物与序列行为 | 用户编辑，或 Agent 用 MCP 制作 |
| Image 2.6 | 生成透明物品与编辑图片 | 前端或 Agent；采用后进入工程 |
| 资产库 | 查找已有素材、区分候选、下载真实文件 | 用户或 Agent 查询 |
| 游戏工程 Skill | 把已就绪资产接入 Godot，设计架构与编写脚本 | 外部 Agent 在指定目标工程中执行 |

### 四个容易混淆的概念

- **任务**：一次执行记录，例如生成、检查、保存或导出。同一作品可能有多条任务。
- **作品**：实际素材。同一动画作业的不同候选是不同版本。
- **草稿**：可恢复的编辑状态。
- **导出包**：可下载、备份或导入其他工具的真实文件。

所以任务数不等于作品数；查到记录不代表文件仍在；检查完成也不等于已采用或已导出。资产库只显示它能读取的持久素材，浏览器草稿需在原工具中恢复。

## 2 安装与启动

### 首次准备

需要 Node.js 22.13 或更高版本；制作角色原图或序列帧还需要 Python 3.11 或更高版本。只做交互物和静态图片编辑不需要 Python。导出 Godot 包无需安装 Godot；实际导入和播放验收使用 Godot 4.7.x。

把仓库放到稳定目录，在根目录执行（Windows 用 PowerShell，macOS 用终端）：

```sh
npm ci
npm run sprite-pipeline:setup
npm run dev
```

- `npm ci` 安装锁定的前端与 Node 依赖。
- `sprite-pipeline:setup` 在 `Tools/SpritePipeline/.venv` 创建 Python 环境并安装锁定依赖，同时以可编辑方式安装物品转换工具 PixelProp（`Tools/PixelProp`）。它不生成图片。拉取新版本后应重新运行一次；换操作系统或换机器时重新 setup，不要复制 `.venv`。

只需要交互物和静态图片编辑时，`npm ci` 后运行 `npm run dev:interactable` 即可。它同样启动全部前端页面，只是不启动 SpritePipeline；交互物动画、物品原图导入与转换都依赖 SpritePipeline，需要用 `npm run dev`。

### 日常打开与关闭

运行 `npm run dev`，打开 http://localhost:3000，保持启动终端运行。在该终端按 Ctrl+C 结束；启动器管理的子服务随之退出，启动前已在运行的外部服务不受影响。

| 服务 | 默认地址 | 用途 |
| --- | --- | --- |
| 前端 | http://localhost:3000 | 导航、专业编辑器、作品预览 |
| Runtime Bridge | http://127.0.0.1:8790 | 任务、文件、图片生成与本地导出 |
| SpritePipeline | http://127.0.0.1:7860 | 角色原图、动画服务和原生操作界面 |

默认 localhost 可能解析为 IPv6，应检查清单指定的地址，不要因另一个回环地址连不上就判定服务离线。前端、Bridge、Sprite API 与 Sprite UI 要分别检查，一个在线不代表全部就绪。

Web API 和 Bridge 校验请求的访问地址与来源。默认允许清单中的前端地址，以及相同协议、相同端口的回环别名。自定义域名或前端端口时，在前端和 Bridge 的运行环境设置相同的 `WORKBENCH_FRONTEND_URL`（实际前端 URL）。它只影响来源校验，不改监听端口或启动地址。JSON 写请求使用 `application/json`；MCP、CLI 和服务间调用无需伪造浏览器 Origin。示例见 `.env.example`。

### 拆分启动和重启

开发时可分别运行 `npm run dev:web`、`npm run workbench:http` 和 `npm run sprite-pipeline`。最后一个同时提供 UI 与 API；`npm run sprite-pipeline:api` 只提供 API，根页面返回 Not Found，不能作为嵌入工作区使用。

改了服务端代码后，旧进程可能仍在运行旧代码。重启前先保存编辑、确认没有正在生成的任务，并确认要重启的是本项目进程；不要直接强制结束占用端口的未知程序。项目没有闲置自动关闭计时器，终端关闭、进程异常退出或旧模块缓存要分别排查。

## 3 模型与密钥配置

### PixelLab（角色原图、物品原图和动画）

在角色原图页面或序列帧工具的“设置”中保存 PixelLab Key。两处连接同一 SpritePipeline 服务，输入一次即可。保存后输入框留空是正常的，看“已配置”状态。

凭据默认存在 `work/sprite-pipeline/config/credentials.json`，Windows 用当前用户 DPAPI 加密，重启后可读。`PIXELLAB_API_KEY` 环境变量会覆盖已存值，此时界面不能修改它。换机器或换 Windows 用户后，旧加密文件不一定能解密。

原图、动画生成以及启用的视觉检查或 AI 修补会消耗外部额度。浏览、模板、资产清单、下载已有文件和本地 Godot 打包都不调用生图模型。

### 角色动作的规划与复核模型

序列帧工具的“模型设置”可分别选择默认规划模型、视觉复核模型和单个专家：

- **API Key 与服务状态**默认展开。TokenHub、OpenAI、PixelLab 分别输入；已保存的 Key 不回填，留空保存即保留原值。同一服务共用 Key，账号需具备对应型号权限。
- **新增型号**：展开“新增或编辑可选模型”，选择 API 服务，填写服务商的准确模型 ID，设定输出上限与请求等待上限，点击“加入可选模型”，分配给专家后“保存配置”。
- 视觉复核可直接选 TokenHub 的 `glm-5.3-flash`（支持看图），与 Kimi 规划共用 TokenHub Key。`glm-5.3` 是纯文本型号，设置界面会拒绝把已知纯文本型号用于看图专家。
- Kimi K3 系列参数自动适配。其输出上限包含推理与正文；较慢的推理模型可调高等待上限。超时和输出截断都保存失败证据，不自动重发。

配置只影响新规划，已有任务保留原模型记录，旧候选的报告不会改名或重跑。

### 图片服务（GPT Image 2.6）

交互物的图片生成面板提供 GPT Image 2.6 设置（实际模型 `gpt-image-2.6-sunburst`），用于透明物品和静态图片编辑。设置经 `/api/workbench/image-assets/settings` 转发到 Bridge 的 `/v1/image-assets/settings`，响应只返回配置状态，不回显 Key。

Key 受保护地持久保存：Windows 用当前账户加密，macOS 用钥匙串，其他系统用权限受限文件，重启 Bridge 后恢复。也可使用 `OPENAI_API_KEY`（见 `.env.example`）。不要把实际 Key 写进任务、对话或提交。旧的 `work/config/map-generation.json`、旧图片提供方别名和 OpenAI 图片端点环境变量仍可读，但不提供旧制作入口。

### 视觉检查凭据

序列帧视觉检查可使用单独配置的服务，默认 TokenHub 混元视觉检查读取 `TOKENHUB_API_KEY`，也支持设置中声明的 OpenAI 选项。图片服务的配置不会自动写入序列帧进程；需要共享环境变量时，通过统一启动配置提供。

## 4 导航与保存

### 从哪里进入

开始页列出角色原图、角色动画、交互物动画、交互物编辑四个工具卡。顶栏主导航依次为角色原图 `/tools/reference-art`、角色动画 `/tools/sprite-generator`、交互物动画 `/tools/interactable-motion`、交互物编辑 `/tools/interactable-editor` 和资产库 `/assets`，齿轮图标进入工作台管理 `/advanced`。旧的 `/player` 重定向到首页。

顶栏标出当前工具，作品名显示在工具自己的工具栏中，制作记录可恢复正在做的内容。

进入页面、查看作品、向 Agent 问方案都不会创建制作任务，只有保存、生成、检查或导出才产生记录。高级工具中的多次执行尝试不是重复作品。

### 保存和下载的区别

交互物浏览器草稿存放在原浏览器、原网站地址的 IndexedDB 中。“保存到资产库”把完整源项目存到本机服务。共享保存、资产保存和 Godot 导出是三个独立操作，保存不会自动生成引擎包。

离开工具前确认保存完成。保存失败时留在当前页，重试保存或下载源文件。交互物导入导出等繁忙操作期间导航可能被阻止。源文件导出才是可换机器的备份。

序列帧作业由 Python 服务保存，原图生成任务由 Runtime 保存，它们都不是浏览器草稿。原图页尚未提交的表单不算已保存，刷新前先记下必要描述。

### 已有图片的局部调整

可调整的对象：交互物的默认图、切换状态图、序列条目静态图，独立图片任务，以及资产库 `image:` 素材。入口分别是交互物中的“局部调整默认图片”，独立图片任务预览或资产库详情中的“局部调整图片”。动画外观槽不能用播放帧代替静态源，动画帧的调整见第 6 章。

**打开与保护。** 交互物会先等工程保存到服务端再打开，冲突时保留本机草稿。工作区打开期间暂停宿主的交叉编辑与离页；状态版本改变后旧会话变为只读，不能强制覆盖。

**本地编辑。** 画笔、橡皮和本地操作（替色、透明噪点清理、填充、擦除、移动、简单换色）各自存为新版本，不调用模型。“打开时的图片”是会话冻结的源图；未保存的笔划在执行其他操作或应用前自动存为新版本。最后需明确应用：交互物点“应用到交互物”，独立图片点“另存为新素材”。

**采用的影响。** 只更新指定槽位，其他状态、行为与碰撞保留。只有采用默认静态图会停用默认待机 / 聚焦动画。“恢复打开时的图片”只把所选图片恢复为一个新版本。采用后要继续精修，需基于当前图片新建会话。已导出的游戏资源不会随源图自动更新。

**AI 局部修改。** 切换到“AI 局部修改”：

1. 用“添加选区 / 减去选区”画硬边蒙版（只改范围，不改像素）；要画局部范围，可先清空整图选区。
2. 填写描述、选择参考，点击“生成 AI 候选（调用模型）”。这是单独的付费提交，本地操作失败不会自动升级为 AI。
3. 基准、区域、描述和参考在提交时冻结。关闭窗口不保证取消请求，断连、刷新和重启不会自动重发。
4. “保留原图透明度”默认开启，保留基准图每个像素的透明度（含半透明边缘）；要增删轮廓时关闭。选区外始终保持原 RGBA，但颜色、内部细节和接缝仍需检查。连续精修以所选候选为准。

任务链接带准确会话和候选，可复制继续查看；历史只读，不会暗改当前来源。

**恢复与失败。** 未保存笔划只有本浏览器的延迟 IndexedDB 副本，受存储容量和基准校验限制，不跨浏览器同步。未提交的 AI 表单也不是服务端候选。保存失败时先检查原会话与任务，再重试相同命令；若提示服务端已采用但本页未同步，不要当作未采用另建提交。详见[图片局部调整](image-editing.md)。

## 5 制作角色原图

### 从描述到参考图

进入“角色美术 → 制作角色原图”，确认 SpritePipeline 与 PixelLab 已就绪。输入角色描述，可指定名称、朝向和像素颗粒：

- 描述宜包含职业、服装、武器、主要颜色和侧视要求，例如：森林游侠，绿色短披风，皮甲，手持短弓，面向右侧，轮廓清楚。
- 尺寸可选 64×64（粗像素）或 128×128（精细像素，默认）。小角色优先在游戏实际显示尺寸下检查 64 像素版本的轮廓。

点击“生成一张原图”，输出为透明背景像素角色，不额外调用付费提示词改写。完成后检查人物是否完整、透明边缘是否正确、手持物与朝向是否符合要求。每次重新生成都是新的请求。

要继续做动画，点击“用于制作序列帧”。工作台把原图导入为可复用角色预设，并在序列帧页预选它。移送保留原图字节和原生尺寸，不缩放、不重画，也不自动创建动画任务。可用简短的 identityDescription 锁定外观，源提示词完整保留。同一原图重复移送复用同一角色身份，内容冲突时拒绝覆盖。只需要原图时，下载 PNG 即可。

完成的原图位于任务目录的 `reference.png`。

### 导入已有原图

已有图片不需要付费重画。`reference-art` 的 `import` 操作接受仓库内的 `sourceImagePath`、补充描述 `prompt`、名称、朝向和 size（64/128），只复制经过校验的透明 PNG，不调用模型，也不需要 PixelLab Key。导入记录标明来源、原始哈希和 `generatedHere:false`，历史中显示“导入素材”，可按原有校验流程移送序列帧。导入记录不能说成真实生图，不改图片，也不倒填生成日期。物品原图的导入与转换见第 8 章。

当前 MCP 没有把任意附件直接注册为角色预设的操作，不能编造角色 ID，也不能把任意图片冒充已完成的原图任务。

### 用 WorkBuddy 制作

可以说：“制作一个面向右侧的森林游侠像素角色原图，只做一张，完成后让我预览。”还没决定外观时，说“只讨论方案，不生成”。Agent 应保留你已给出的选择，只询问影响成品的缺失信息。

## 6 制作和审查动画

角色动画的主流程在“角色美术 → 制作玩家”，分五步：准备与描述、查看制作方案、自动制作、检查与调整、导出与使用。规划、绘图和视觉复核三类调用分别计费，额度在准备页展开预算后可调整。

### 准备与描述

从作品库选择已有作品，或选择真实角色和动作；从原图移送来的角色会预选。首次试做通常用一个候选，帧数、速度和循环沿用动作预设，你明确要求的参数优先。候选是同一批生成的不同版本，要三份就明确说三份，它们不是一个合成动作。历史素材的帧数和尺寸可能不同，不能假定都是 16 帧或规则 4×4 表。

新任务默认使用“独立专家与争议复核”：每候选视觉调用上限 25 次，展开预算可查看或改用基础检查。详见[视觉专家与争议复核](sprite-review-evaluation.md)。

**可选：结构解析与纠正。** 一次解析识别原图部件和锚点（一次语义模型调用，可在模型设置中单独选择“角色结构解析”模型）。点击“查看结构”叠加检查，按需纠正、保存或恢复旧版本；查看、刷新和手动纠正不再调用模型，也不改原图。核对后勾选“使用已核对的结构辅助本次制作”才会生效，只确认结构不会自动启用。未知部位仍保持未知，不会因确认而变成确定的控制位置。详见[角色视觉结构](visual-structures.md)。

### 查看制作方案

点击“制定方案”才调用规划专家。查看方案时关注动作事件、装备归属、结束姿态和节奏，不只看阶段名称；动作约束与关键姿势默认收起。

**规划进度。** 以每位专家最近一次调用为准。“已提出建议”“已提交方案”只表示收到意见，不代表可以绘图；本机校验拒绝时显示“校验未通过”。无效回复、请求失败或中断显示明确状态并停止转圈。带关键问题的方案仍需补充，不算通过。

**重新规划。** 失败后可直接点“重新制定方案”，沿用当前要求并保存新版本，无需先改提示词；按钮旁显示本次规划调用上限。也可先“返回准备与描述”修改要求。重新规划会再次调用模型，旧版本与费用记录保留；成功后仍需另行确认开始制作。

**段末姿势。** 方案页直接说明有几段绑定了真实图片，未绑定的段使用文字要求。有合适图片时，展开“用已有图片约束段末姿势”，检查后绑定同尺寸透明 PNG。图片在本地保存，不调用模型；它只是引导，不替换实际输出的末帧。原图结构辅助不会自动提供目标姿势图。

### 自动制作与分段检查

确认方案后才开始绘制。每段完成后显示“确认第 N 段”：

1. 播放当前完整片段，拖动逐帧条核对目标末姿势、装备和节奏。
2. 勾选检查确认，填写结论；模型意见未通过时需明确裁决。
3. 点击“确认此段，继续制作”。实际末帧锁定为下一段的起点。

模型说通过也不能替你确认，WorkBuddy 可以取得同一组实际帧代为检查。刷新会保留当前检查点，普通继续按钮不能绕过检查。

- **目标姿势提前到达**：若目标姿势出现在较早帧、最后几帧已越过目标，展开“目标姿势提前到达时，选择实际锚点”，选择准确帧、勾选采用范围并记录原因后再确认。其余原始帧保留在记录中，下一段从所选帧继续。系统不会自动截取。
- **片段不合格**：填写停止原因，点“本段不合格，停止后续制作”。已确认片段和原始帧保留，不会自动付费重画；返回描述修改方案时建立新版本。
- **暂停与离开**：可以暂停后续请求、刷新或稍后回来，已提交的片段会继续取回，不自动重发。

### 检查与调整

最后一段确认后，仍需检查完整动作与片段衔接。先正常播放，再慢放查看问题帧：轮廓、衣物、武器、肢体、脚底高度、透明边缘和动作衔接；循环动作看尾帧到首帧，攻击动作看准备、出招与收势。文件存在、QA 报告生成或 GIF 首帧可读，都不能证明动画好用。

主页面只保留动画、简短结论与确认操作。“检查详情”查看专家依据和帧证据，“高级工具”管理结构、锚点及停止制作。

**视觉报告。** 分段与整段都先做基础检查，再由外观和运动专家各给一次独立意见，有争议时最多再复核一次。报告区分“看不清”“可能遮挡/透视缩短”和“具体外观矛盾”：看不清不自动判错或通过；独立专家指出的矛盾未解决时，即使最后复核清除了它，仍需你看实际帧确认。节奏偏好标为可选优化。带质量合同的任务还提供完整性、装备一致性、节奏三项报告。修改帧后旧报告失效；播放确认绑定当前帧，外部改帧后需重新确认。

**结构观察。** 从“高级工具”进入，默认本地追踪，不调用外部模型；勾选关键帧核对才增加最多一次语义请求。可查看部件叠加、按当前帧纠正或恢复旧版，均不修改动画。若参考区域一开始就圈错，先在第 1 帧纠正该部件，新观察会优先使用这次纠正，后续帧仍需检查。另行开启结构辅助复核前会显示最多三次视觉请求。

**调整部分帧。** 点击“调整部分帧”进入专注修改，返回按钮回到动画检查。这用于明确修改，也接受个人偏好，原版通过检查也可以调整：

1. 选择连续范围，填写要求（或按当前范围的专家建议试做），点击“生成一个备选”。你的原话优先于建议。
2. 128 像素原帧一次编辑 2 帧，限制的是选中数量而非帧号；未锁定的段尾也可选，例如 15–16。奇数、单帧、反向范围和保护锚点会分别提示，不自动凑帧或拆分收费。
3. “精确限定修改区域”是默认关闭的可选画笔，勾选后逐帧涂选，区域外像素才有硬保护；不勾选时以原姿势为基础，未要求的内容应保持。
4. 备选出现后同步播放、填写结论，再采用或保留原版。完整候选采用会建立新版本；未选中帧按文件哈希保护，原版、失败记录和导出保留。

试做次数按帧计算：每帧最多参与两次绘图，页面显示当前选区剩余次数（例如改过 13–14 帧后仍可选 15–16 帧）。不同窗口互不占用，重叠帧沿用已用次数。尚未绘图的需求理解失败不占绘图次数，此时没有新版，也不显示“保留原版”；已提交但失败或结果未知的绘图仍计数。恢复入口只在请求中断时出现。费用、尺寸限制和 MCP 操作见[选帧修改与备选版本](motion-adjustments.md)。早期任务中的“只修复这一段的局部问题”记录仍可在“旧版局部修复记录”中查看。

### 采用和导出

采用前需播放完整动作、逐帧查看并核对提醒，勾选播放确认，写下至少 4 个字的检查结论，并明确接受已核对的技术提醒。按钮不可用时，底部会说明还缺哪一步；有阻断或待修补帧时先处理，不能强行采用。未通过模型检查的结果也可以在人工检查后接受，但必须写明结论并确认提醒。

导出使用已确认的播放帧序，原始返回完整保存。导出得到精灵表 PNG、预览、配方与 QA，以及 Godot SpriteFrames ZIP。已采用的候选可反复进入导出：播放检查中显示“已采用：返回导出”，只导航、不重复审批；作品库的“导出”会恢复所选候选的 PNG、Godot 包和附加文件。历史 PNG 若没有 Godot 包，会提示以新文件名导出完整包，旧文件保留，重新打包仍遵守原检查门槛。

点击“导出到 Godot 项目”打开项目选择窗口，见第 7 章。修改需求会建立新版本，历史版本和素材保留。

### 旧版工作区

旧任务和旧预设可从制作记录的“旧版工作区”（`/tools/sprite-generator?legacy=1`）进入，使用“1 · 生成 / 2 · 播放检查 / 3 · 逐帧修补 / 4 · 导出”标签：

- 逐帧修补保留原始版本，保存时校验当前帧版本并使旧审核失效，随后需重新检查。外部整帧替换需按流程标记待修补；AI 修补的新结果先预览，再明确采用。
- Agent 执行 approve 时必须给出实际看过画面的 reviewNote；acknowledgeWarnings 只能用于明确接受已检查的警告。门禁会检查候选状态、QA 与源文件一致性。
- 不要为通过导出跳过硬错误、覆盖较新的帧或随意接受警告。

从逐帧编辑返回时，顶部“返回当前作品”回到相同版本与候选；先保存修改，再返回重新检查。

### 继续已有候选

可以说：“打开最新一次连续三个候选动画的第 2 个候选，只看，不生成。”Agent 应按批次和候选条件进入那一版的详情页，而不是停在作品库首页。有多个合理结果时显示名称或预览让你选；指定候选不存在时明确说明。

## 7 把动画导入 Godot

### 导出到游戏项目

角色工作区、交互物组装和资产详情都有交付入口，打开同一个项目选择窗口：

1. 首次点“选择项目…”，在页面内浏览包含 `project.godot` 的游戏文件夹并点“使用这个项目”，或直接粘贴游戏根目录。选择会被记住。
2. 点击“导出到此项目”。
3. 点“复制给 WorkBuddy”取得精确的交付和接入请求，或在 WorkBuddy 说“接入刚导出的资源”。

Agent 负责资源安装、场景挂载、动画合并和交互脚本连接，无需手动解压或改 res 路径；只合并本次动作，保留其他动作与控制器。已有导出可通过“选择游戏项目并交付给 WorkBuddy”再次交付。“等待 Agent”“资源已安装”“代码已接入”“引擎已验收”分别显示；网页不会自行启动 WorkBuddy 会话，导出成功也不代表脚本已接好。“仅下载 ZIP”仍可用，独立 SpritePipeline 的 ZIP 下载也保留。详见[完整交付流程](godot-delivery.md)。

安装进程异常退出后，下次接入可回收同一主机上已确认退出的进程留下的安装锁。活进程、旧格式、空锁或无法确认归属的锁会保留；持续提示忙时先检查进程、未完成的接入与安装记录，不要直接删除不明锁。

### 手动导入资源包

下载“Godot SpriteFrames 包（ZIP）”，解压后把整个 `forge_sprites` 文件夹放到 Godot 4.7.x 项目根目录，保持目录结构。

| 包内文件 | 使用方式 |
| --- | --- |
| sprite-sheet.png | 已审核候选的精灵表纹理 |
| sprite_frames.tres | 已装配帧、动作名、FPS 与循环的 SpriteFrames 资源 |
| animated_sprite.tscn | 可拖入场景的 AnimatedSprite2D 视觉节点，运行可播放 |
| export.json | 来源、候选、帧序与导出参数 |
| IMPORT.md | 本包的导入说明 |

目录按角色、作业和候选隔离。包不含 `project.godot`，不覆盖项目设置。移动资源时在 Godot 编辑器内移动并核对引用，不要只把 `.tres` 单独拷走。

给已有 AnimatedSprite2D 使用时，把 `sprite_frames.tres` 赋给 Inspector 的 Sprite Frames 属性即可，无需手动切图。快速预览时，把 `animated_sprite.tscn` 拖进场景运行。

### 更新已有多动作角色

导出包只含所选的一个动作。直接用它替换整个角色资源，会丢掉其他动作。应由工程 Skill 把本次动作合并进原资源副本，再更新引用，保留 idle、walk、jump 等动画。

导出保留帧区域、顺序、动作别名、运行 FPS 和 loop；示例场景按角色锚点设置脚底原点并使用 nearest 过滤。只替换 SpriteFrames 不会调整旧角色的偏移、缩放或碰撞，需结合实际角色检查。

### 最小人工验收

在 Godot 中选中资源，核对帧数、顺序、动作名和速度。运行场景：循环动作应连续，非循环动作应正常结束；再检查左右朝向、脚底位置和重复触发。导出成功只证明包已生成，以上操作才是引擎中的实际验收。

## 8 制作交互物

### 准备物品原图

**生成。** 选择物件后展开右侧“生成物品原图”，描述单个物品（如电池、宝箱、开关），点击生成。与角色原图共用 PixelLab Key，输出 128×128 侧视透明 PNG，每次生成消耗额度。透明物品也可通过 Image 2.6（`image-assets` / `generate-prop`）生成；已有图片可显式 `edit-image`，确定性处理用 `process-image`。GPT 图片使用自身尺寸规则，不能直接作为动画参考。

**导入或转换。** 已有 128×128 透明 PNG，用“导入 PNG / 从物品图转换”中的“导入 128 px 物品原图”；只有 GPT Image 生成的大图时，用“从物品图转换”调整预设和参数，对照源图与 1×/4× 结果后保存。两者都在本机处理、不消耗额度。命令行可直接运行 `npm run pixel-prop -- convert <源图> -o <输出>`。对应 MCP 操作为 `reference-art` 的 `import`（`subject=prop`）和 `convert-prop`。

**采用。** 先检查预览，再下载 PNG 或点击“采用到当前物件”。采用会替换默认图片并停用默认待机 / 聚焦动画，保留已有动画帧、状态专用图片、其他素材和行为。生成不会自动采用或生成动画；切换物件后以采用按钮上的目标名称为准。草稿自动保存，可从最近物品原图或资产库的“物品原图”恢复。

**用作动画起点。** 导入或转换的物品图需写确认说明（核对视角、初始状态、部件完整和透明背景），再点“用作交互物动画对象”；MCP 移送须带 `confirmation.note`。

通过 WorkBuddy 可以说：“为当前电池物件生成一张侧视像素原图，先预览，不要改行为。”只要求图片时不会创建角色预设。详见[物品原图](prop-art.md)。

### 复用资产库素材

交互物编辑器可从资产库直接导入图片、动画和完整项目，无需下载再上传。导入不生成、不增加后台任务，保留版本和源文件。详见[内部素材导入](internal-imports.md)。

### 制作状态动画

切换或序列物件需要开关、点亮等状态动画时，在左栏“素材”点“制作状态动画”。工作台保存工程后打开交互物动画面板，并带上当前工程与物件：

1. 在左侧状态图写好各状态的名称与外观（切换物件默认两个状态，序列物件按条目）。铰接或形变动作在“部件结构”中选择已核对的结构。
2. 制定方案、确认制作。每段过渡生成后在中间画布逐帧检查，可先只确认状态帧。
3. 需要修正时用“工具”页签：固定部件回填、对齐、清理、旋转草稿或选帧修改。结果都是备选，对比后再采用。
4. 在“写回”页签把状态图和过渡写到切换 A/B 或序列条目，可调整逐帧节奏或往返播放，并在场景预览中检查“触发 → 过渡 → 停在新状态”。

规划与生成按实际调用计费，确定性工具不计费。详见[交互物动画面板](交互物动画独立面板方案.md)。

### 先选行为

从首页进入交互物编辑器。没有外观图也能先做逻辑草稿，但它不算完整美术成品。导入图片或序列帧后，分别调整外观、感知范围、点击区域和自身碰撞。

| 行为 | 常见用途 | 成功后的结果 |
| --- | --- | --- |
| 查看 inspect | 告示牌、说明物件 | 展示内容，可重复或一次完成 |
| 切换 toggle | 门、开关 | 在两种状态间切换，可改变外观和碰撞 |
| 拾取 pickup | 收藏物、道具 | 发出一次拾取事件，可保留、隐藏或释放 |
| 序列 sequence | 多阶段提示或装置 | 每次成功推进一步，到末项按配置处理 |

“只能开一次的宝箱”不一定是“拾取整个宝箱”：先决定打开后是否保留箱体、是否给奖励，再选行为。背包奖励由游戏代码接事件实现，编辑器不会替目标游戏创建背包系统。

### 设置和预览

触发方式有靠近按键、点击、自动进入和外部调用，默认按键为 E。需要播完再结束的动画或音效应设置等待，要求等待的动画不能无限循环。

预览可模拟靠近、离开、按键、点击和两个物件重叠，用于检查反馈、最近物件选择和状态变化，但不模拟正式人物的移动物理。完成状态属于每个实例，复制的物件不共享拾取进度。

通过 WorkBuddy 可以说：“制作一扇靠近按 E 可开关的门，先保存逻辑草稿，不生成美术。”Agent 应取模板、保持对象 ID 并 save-project，再给出编辑链接。接着说“把按键改为 F 并导出 Godot”，应修改同一对象，而不是新建同名物件。

网页和 Agent 通过同一 Bridge 读取、保存和编辑交互物文档。写入携带 expectedRevision 与稳定 commandId，冲突时重读，不覆盖他人修改。validate / simulate 只检查已保存版本、媒体与有限事件，不代表真实音频、游戏存档或 Godot 验收。详见[交互物编辑器](interactable-editor.md)。

### 导出和接入

导出不需要 PixelLab、SpritePipeline 或已安装的 Godot。保存源文件可继续编辑，导出 Godot（`export-godot`）才得到运行资源包。

通用包整体放入目标项目的 `addons/workbench_interaction` 目录。每个关卡放一个 `interaction_runtime_2d.tscn`，再放所需的 `object.tscn`。靠近交互的人物物理节点要加入 `interaction_actor` group，且物件感知 mask 要包含人物的 collision layer；只给普通 Node2D 加 group 不会产生物理重叠。

游戏代码连接 `picked_up`、`toggled`、`interaction_finished` 等信号来处理奖励、剧情和输入。导入多个包时保持 runtime/v1 一致，不要盲目覆盖旧版运行时。

## 9 查找、交付与清理资产

### 正确查找

资产库按角色原图、物品原图、动画和交互物展示持久素材；浏览器草稿和只下载到本机的源文件不会收录。用名称关键词和类型过滤，查全时要翻页，Agent 应带回 nextOffset 和 snapshot 完成分页。制作历史用于追踪执行，不能代替资产盘点。

同一动画候选的创建、检查与导出关联到同一资产，不同候选分别保留。时间未知就保持未知，不能把最近打开时间当生成时间。出现服务离线或部分覆盖提示时，先恢复来源，再判断是否缺项。

清空制作历史只归档执行记录，不删除或隐藏作品。资产详情的“来源文件与版本”保留首次创建时间和制作 / 导出记录，可点击追溯已归档任务。制作历史支持超过 200 条的读取与搜索，不必为找旧作品而重新制作。

### 下载和交接

勾选资产后点击“下载所选素材”，得到真实 ZIP：原图提供图片；动画包含有序 PNG 帧及已有的 GIF、精灵图和 Godot 包；交互物包含源工程及已有引擎包。未导出的作品也可下载当前素材，但下载不改变审核状态。

每次最多 100 件，源文件总量上限 128 MiB，超出时分批。缺文件或打包期间内容改变会报错，不会给出假完成或残缺文件。

Agent 的 get_asset_manifest 返回可读说明和结构清单，适合交接来源、尺寸、帧率与哈希。它不复制素材，两个描述 JSON 不等于可用资产；工程接入时要同时提供已选文件或真实包。

### 移入回收站与恢复

在资产库悬停素材，勾选右上角选择框，点击“移入回收站”并核对列表后确认。动画的每个候选可单独选择，详情页也能移入。在“回收站”中勾选素材，点击“恢复所选”即回到资产库。切换范围会清空选择；跨页选择会保留，并在确认窗口完整列出。

回收站保留源文件、制作记录和已有引用，不释放磁盘空间，也不提供永久删除。原工具仍能访问这些素材；来源离线时可以恢复目录状态，但无法修复另行删除的源文件。

管理页的“删除浏览器项目与草稿”只清理当前浏览器中的交互物、制作草稿和未保存的图片笔划，保留后台任务、已保存素材与导出文件。清理前先下载要保留的源文件；清理后旧页面不能把原草稿写回，需刷新后重新编辑。

### 看起来丢失时

先确认使用的是原来的浏览器和 http://localhost:3000，再检查 SpritePipeline 数据目录与服务是否在线。独立版可能把作业存在系统用户目录，而工作台默认使用 `work/sprite-pipeline`。启动器有受控的一次性旧资产导入，同名冲突保留在 recovery，不做双向同步。

不要靠清空 work、outputs 或浏览器数据来修复列表。先读取来源范围、目录和导入记录；未被当前目录索引不等于已删除。

## 10 让 WorkBuddy 正确使用 MCP

### 接入步骤

在 WorkBuddy 打开本仓库，配置名为 `2d-game-workbench` 的 STDIO MCP：命令 `node`，参数 `scripts/workbench-mcp.mjs`，工作目录必须是仓库根目录。仓库提供 `.mcp.json`；Codex 等宿主的专用配置按[客户端接入](agent-clients.md#mcp-配置)在本机创建。配置文件存在不证明宿主已加载。

连接后通过工具发现确认实际工具面，完整名单以 manifest 和 MCP discovery 为准。新增工具或更新 MCP 后需重新连接；只新开聊天不一定重启旧 server。

**配置变更后找不到原生工具。** 新增 `FORGE_MCP_HOST` 等环境变量后，WorkBuddy 视为配置变更，旧的信任记录失效。到连接器 / MCP 管理中找到 `2d-game-workbench`，检查命令和参数后重新信任，再重连并新建项目会话。仅重启、确认配置未禁用或 CLI doctor 成功，都不能证明原生工具已挂载。见[Agent 客户端接入](agent-clients.md#配置存在但原生工具未挂载)。

### 会话预览与页面跟随

WorkBuddy 在新会话的首条用户消息后检查前端，离线时启动一次并等待就绪，再用宿主自己的 present_files 打开内部预览；握手后尚无用户消息时不开网页是正常的。正常的新会话应先打开内部浏览器，再提交生成，旧会话或其他浏览器的页面不算本次开页。

若看到 `preview_required`，说明尚未创建任务、也没调用生图 API，Agent 应先执行宿主的开页动作，连接后用原参数继续，无需重输 Key。宿主缺少开页工具时，Agent 必须明确说明，不能只给链接就称已打开。

执行时右下角显示当前作品与步骤，页面随原图、动画、交互物保存和导出切换，无需逐步说“打开”。已有作品优先进入精确详情。暂停跟随或手动离开后停止切换，继续跟随可恢复当前步骤；正在输入、工具忙碌或保存失败时保留原页面；用户关闭预览后不强行重开。看不到当前作品时，让 Agent 用 workbench_get_frontend_context 确认页面摘要（只含名称、身份和编辑状态）。页面到达不等于作品通过审核。详见[步骤跟随与验收](agent-preview-follow.md)。

### 对话范例

- “盘点已经保存的素材，按类型统计，指出还缺哪些文件；不要生成。”——资产核查。Agent 应查全请求范围，并说明浏览器草稿不在目录内。
- “用这份已选角色制作向右行走，一个候选，其余沿用预设，检查后交付。”——明确制作。Agent 使用真实角色与动作 ID，不再问已给出的选择，实际审查通过后才导出。
- “只设计一个能跑跳、开门的小关卡，先不改文件。”——工程规划。Agent 先查资产与工程并提供方案，不建生产任务，也不写入游戏。

Agent 需要澄清时，优先用宿主提供的 AskUserQuestion 或等价工具（先读其 schema）；没有就简短提问。取消或未答复不等于批准推荐选项。正常回复应说明结果、给出准确预览或链接，再提一个有用的下一步。

## 11 从资产到游戏工程

### 工程 Skill 的前提

使用 forge-game-engineering 时，提供目标游戏目录和要完成的可玩范围，例如把已选行走与攻击动画接到现有角色，或把已导出交互物接入指定关卡。同时提供参考工程时，须与待修改工程分清，参考工程默认只读。

Agent 应读取目标 `project.godot`、架构文档、场景、配置与相关脚本，从目标工程现有的场景结构、控制器和生命周期出发，不能因素材齐全就引入另一套通用框架。

### 角色帧和动作

优先使用已有的 Godot SpriteFrames 包。旧资源需重新整理时，工程 helper 从显式有序 PNG 或 atlas 区域生成资源，记录候选和源哈希；不能按目录字典序猜帧顺序，也不能把精灵表空格当有效帧。

保留正式角色场景的 Sprite 节点、控制器、视觉偏移和碰撞。部分动作更新用 `sprite_frames_merge.gd` 合并到原资源副本。动作别名须与实际工程对应，例如 hurt/hit、death/defeated 的命名可能不同，需明确映射。

状态改变时切换动画，同一次更新不能每帧重置到第 0 帧。重复攻击需要新的动作触发，即使逻辑状态名未变。攻击前摇、持续时间与命中由原控制器负责，不能把 QA 重点帧或动画播放结束当作伤害事件。

蓄力、突进或技能可能临时接管动画（如 Cyber）。替换时保留这些控制权与固定帧引用，检查新资源是否有相应帧，不能只看普通行走能播放。

### Helper 的用途

`stage_assets.py` 在新的输出目录暂存角色动画；`character_visual.gd` 负责表现层播放；`sprite_frames_merge.gd` 合并指定动作。

Helper 不会自动合并到游戏、不生成美术、不需要 API Key。Agent 应先检查暂存结果，再执行用户授权的目标项目改动。自定义控制脚本放在生成资源目录之外，以免再次导出时被覆盖。

### 验收层级

“已写代码”“已暂存资源”“引擎导入通过”“实际播放通过”“画面人工检查通过”“全游戏通过”是不同结论。设置 `GODOT_47_BIN` 后运行 `npm run test:engineering` 可执行隔离的 4.7.x 契约检查；未配置时引擎部分跳过，不能报告为通过。

目标工程最终仍需测试输入 → 状态 → 动画、重复攻击、暂停、朝向、碰撞、离开关卡再进入及实际依赖。fixture 或资产播放器通过不能替代真实游戏验收。

## 12 备份、更新与故障处理

### 备份清单

| 数据 | 默认位置或导出方式 | 迁移注意 |
| --- | --- | --- |
| 共享任务 | work/tasks | 与关联 outputs 一起保留 |
| 原生动画与角色 | work/sprite-pipeline | 保留作业、角色与导入记录 |
| 真实产物 | outputs | 保留原图、帧、包与元数据 |
| 交互物草稿与共享工程 | 保存源文件或导出 ZIP，并备份 work/editor-documents | 保持项目与对象 ID；IndexedDB 不随 Git 迁移 |
| 凭据 | 本机 .env 或受保护服务设置 | 私下保管；跨机器可能需要重新输入 |

重要项目更新前，先保存草稿、备份源文件，并记下仓库提交及数据目录。安装依赖只恢复程序，不恢复浏览器草稿；Git 同步也不包含被忽略的用户资产。

### 更新序列帧组件

维护者先检查 git status 和本地集成补丁，再核对上游版本。`Tools/SpritePipeline` 含工作台特有的链接、下载、资产目录和 Godot 导出接线，不能整目录覆盖。更新后运行组件及接口回归，再重启旧服务。

更新本地工作台、提交主仓库、推送远程主仓库、更新独立序列帧仓库是四件事，要分别报告证据。不能因本地出现按钮就称远程已更新。

### 常见故障

| 现象 | 先检查什么 | 处理方向 |
| --- | --- | --- |
| 页面出现 Not Found JSON | Sprite 是否以 API-only 启动 | 保存工作后启动 UI 模式，检查根页面 |
| 提示接口不兼容 | 是否仍运行旧 Python 服务 | 确认进程归属后重启，不靠重复 start 修复 |
| 动态模块无法加载 | 前端模块 HTTP、依赖与 Vite 缓存 | 修复对应依赖或缓存，重启前端并刷新 |
| 前端连不上 | 清单地址、进程、端口与启动日志 | offline 才尝试启动；冲突或 unreachable 先诊断 |
| API 提示请求来源不受信任 | 当前访问域名/端口与 WORKBENCH_FRONTEND_URL | 在前端与 Bridge 配置实际前端 URL 后重启，不关闭来源检查 |
| PixelLab 输入框空白 | 已配置状态及数据目录 | 不先认定丢 Key，检查环境覆盖和原存储 |
| 图片服务缺少 Key | 当前服务进程与受保护配置状态 | 在图片设置保存，或使用本机 .env 的 OPENAI_API_KEY |
| 旧素材列表缺项 | 数据目录、来源服务、浏览器和分页 | 恢复正确范围，不先清空或重新生成 |
| 任务多于作品 | 是否含查询、检查、导出记录 | 用资产库按真实候选盘点 |
| 旧作品没有 Godot ZIP | 原导出是否早于新增格式 | 保留旧文件；需要时按门禁重新导出 |
| Godot 动画缺失或卡首帧 | 单动作覆盖、别名或每帧重启 | 合并动作并检查控制器触发逻辑 |
| 交互物靠近无响应 | 人物物理节点、group、layer/mask | 按通用包接入约定核对 |

动态模块错误可能来自前端进程中断，也可能来自测试和开发服务共用依赖缓存，不能据此判断“放久了后端自动关闭”。项目测试已使用独立缓存目录，维护时保留这一隔离。修复前端缓存不需要删除用户草稿和资产目录。

反馈问题时，说明从哪个页面进入、做了哪一步、实际与预期的差异、能否稳定复现。任务 ID、错误和日志按需补充，并去除凭据。
