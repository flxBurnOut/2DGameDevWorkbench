# 角色视觉结构

## 前端历史版本预览与恢复

原图“结构解析与纠正”以及动作“结构观察 → 确认或恢复结构版本”均提供“结构历史版本”。列表包含全部已保存版本与说明，可直接选择较早版本，查看当时的部件蒙版、锚点、关系和观察纠正；时序预览可独立逐帧查看。选择历史只读取不可变快照，不改当前结构、草稿、生成绑定或审批。

“恢复为版本 N 的内容”始终带当前结构的 revision/token、所选历史 revision 和稳定请求标识，服务端继续核对原图、真实帧与参考结构哈希。恢复创建新版本，原版本和中间修改继续保留，且需要重新核对。未保存草稿、正在计算、只读作品或来源已变时禁止恢复；历史查询发现服务端已有新版本时先刷新当前结构。恢复应答未确认时可刷新当前版本查看结果；直接重试沿用该次请求，不以旧预览 token 写入。

验证：`node tests/authoring-gaps/run.mjs` 覆盖较早版本指定恢复、当前写入基线、来源/版本冲突及外观约束隔离；`node tests/authoring-gaps/web-server.mjs` 启动完全隔离的浏览器验收，原图和时序各有三个可辨认版本，可检验非相邻恢复、迟到读取、请求重试与来源变化。该 fixture 模拟所有接口，不连接生产服务或调用模型。

## 规划稳定性与可见性核对（2026-10-28）

正式新建和显式重规划使用 `generation_policy_version=5`，新工作冻结
`visibility_review_version=4`。旧任务、失败试验和已保存报告不追溯改写；选帧修改
继承来源工作的复核版本，不在升级服务时悄悄换规则。

策略草案与执行说明分离：`StrategyDraftStage.prompt` 是分析草案，安全上限 4000
字符，不能提交绘图。原有协调专家在最后一轮编写完整、最多 1000 字符的
`stage.prompt`。本机不追加详细分析、不截断、不删关系、不增加压缩或重试调用。
最终说明包含外观、动作、相机、朝向、发力、支撑、轨迹、节奏、姿势、关系、结束、
边界这 12 个通用条件段。各段共享总预算；详细运动与关键姿势仍进入检查合同，
不采用旧试验的 26 字微型限额，也不写死具体动作。

规划为尚未执行的专家预留额度。若可选质询/放大观察会挤掉既定后续环节，其原始
请求、已有意见和 `deferred_request` 被保留，转交已安排的协调者；不假装质询已经
执行或疑问已经解决。足够的预算仍可进行原有协作。真正缺少的用户选择进入
`plan.questions`；无效响应仍停止，不靠删字段或无限循环获得通过。

可见性核对复用两次基础检查、两位独立专家和最多一次争议复核，总上限仍是五次。
记录真实帧中的可见程度、遮挡/投影/特效解释、直接矛盾与前后证据。证据帧列表
可以共享接缝帧，它们不是互不相交的连续时间区间；所有引用仍必须对应实际图片。
未知不能直接判作消失，也不能证明无害遮挡。明确可见的断裂、增生或身份改变
仍保留。版本 4 复用版本 3 的模型提示与结构，只增加本机的矛盾保留：若独立
专家指出具体外观矛盾、最终复核却建议通过，保留待人工裁决，不以一次相反意见
清除证据，也不投票确定谁正确。原始意见、复核建议及规范化结论分别保存。
选帧修改继续分别检查目标改善和未要求内容退化，不增加控件、调用或自动重画。

验收：同一角色与“角色向前挥砍”真实走完四位专家及本机校验，4 次 Kimi，最终
说明 746 字符，可进入制作确认。三份旧素材用于可见性校准：认可主段从确定丢失
改为遮挡/投影不明；旧完整动画的武器维度保持可接受；失败修改的两位独立专家
识别出外形问题，但最终复核仍误判，已通过本机保护保留分歧，用户拒绝状态不变。
最后的冲突保护用原始真实响应免费重放，不能冒充又做了一组新模型实验。

三次分别授权的验收累计 14 次 Kimi、10 次 GLM、0 次 PixelLab。失败记录全部
保留，无图片改写或自动采用。这是一次完整规划成功及有限样本的误判防护验证，
不是准确率、泛化或新动画画质提升的统计证明。模型仍可能看错。真实首末 PNG、
结构引用、检查点和人工采用门禁不变；条件覆盖也不代表硬骨骼控制。

### V4 启动与研究边界

本轮稳定性验收之后可进入 V4 的数据约定和已有素材联合预览，不以同一动作达到
完美为前提。原计划允许 V2 之后先验证这一离线接口；不得因此宣布 V3 结构辅助
相对基线的普遍质量收益已证明。V4 的付费联合生产仍要单独验收。

动画负责人输出实际帧时间、朝向/缩放、足点与交互点及不确定状态；场景负责人
提供物件状态、接触点、坐标转换、遮挡关系与状态响应；第三位成员整理素材来源、
复现记录和人工标注。先用现有素材验证至少两类关系及位置/时序错配反例。UI 只在
原预览中增加按需的角色/联合效果视图，不再扩展主导航或堆叠专家面板。
离线联合预览不等于双管线协同生成，也不等于 Godot 联调通过。

## V3 绘图条件优化（2026-10-28）

隔离实验可冻结 `generation_policy_version=1/2`。2026-10-28 的规划可靠性未通过；
后续用户认可实际动画，指出武器不可见更像遮挡，不能沿用早先“消失”的确定结论。
没有正式采用，也未证明新策略相对旧策略的普遍质量收益。当时默认仍为 `None`；
随后策略 5 完成规划验收后用于新任务。策略 1/2 的记录及既有 V3 结构功能均保留。实验质量合同仍为 v4，严格 JSON 传输与
复核协议不变。`generation_conditions.py` 将相机、朝向、发力顺序、支撑、轨迹和
外观逐项编入绘图输入；已核对结构的任务相关关系仍用独立的 `generation_hint`
表达，不再与运动条件挤在同一条摘要内。关键姿势、段内节奏与边界同时传递。
这些是文字及图片条件，不是骨骼、轨迹硬锁定，也不包含具体动作模板。

策略 2 另将可发送字段的长度预算写入策略/协调专家的 JSON Schema，并在本机重复
验证。6 个关键姿势、3 个停顿范围与全部运动字段均预留容量；停顿原因、完整推理
和进入/离开说明保留在复核合同，绘图传递明确停顿范围。策略 1 的既有实验记录
仍使用原编译器，不升级、不截断旧返回。

整条提示仍限 1000 字符。规划说明预留文字容量，本机超限时报告各项长度并拒绝，
不截断、不删除关系、不增加绘图请求。未记录此策略的旧方案保持原提示与哈希；
诊断 fixture 默认兼容历史合同，新策略测试显式启用。选帧修改协议不改动。

原生 `submit.intent.json` 中的 `drawing_conditions` 保存逐项来源、提示哈希、
结构引用及实际首末图哈希。`target_mode=text_only` 表示未绑定末图，不能宣称已
执行姿势图片控制。方案页默认显示绑定段数，上传仍在原有可选区域，不新增控制面板。
不自动选择历史姿势或生成目标图片；目标 PNG 仍需检查、明确绑定和冻结。

质量对照固定同一方案的段数、帧数、FPS、种子、参考及目标图片，再比较编译策略。
若重新规划改变这些条件，必须明确记录，不能把全部差异归因于结构。实际上一段
输出仍是下一段首图，不得为了让两组输入一致而替换真实中间帧。旧兼容、条件送达
与真实视觉收益分开验收；技术通过不等于 V3 质量通过。

角色动作准备页提供可选的原图结构解析；检查播放器增加可选的 **V2 时序观察**。
静态结构保存部件、可见区域、锚点和关系；时序观察在实际帧中追踪部件，
支持局部纠正、版本恢复和独立的结构辅助复核。阶段是否通过以对应验收记录为准。
V3 可显式选择已核对的静态结构辅助制作；V4 人物—物件交互尚未接入。
结构观察本身不自动修改或采用动画；实现通过与真实质量对照通过分别记录。

## 使用流程

1. 选择角色，展开“结构解析与纠正”，点击“解析角色结构”。
   一次分析最多调用一次已选语义模型；本地 SAM 分割不调用外部 API。
2. 默认继续显示原图与简短状态。点击“查看结构”，选择需要查看的部件或锚点。
   青色标记表示可见位置，黄色表示推断；未知位置不画成确定坐标。
3. 需要修改时进入“纠正位置或关系”。点击原图放置锚点，或给部件添加保留点、
   排除点、拖动框选区域；可补充遗漏部件和锚点。保存只重算改变的局部结构，
   不调用语义模型、不改变 PNG。这里的区域属于观察数据，不是动画编辑蒙版。
4. “恢复上一个结构版本”创建一个恢复版本，保留全部历史。刷新会读取原记录；
   尚未提交的纠正草稿按分析身份保存在当前浏览器。不同版本的草稿不强行覆盖。
5. 核对后可确认结构。坐标落在透明区、区域缺失等问题会阻止确认。
   确认不会把未知/推断改成可见事实，也不会触发绘图、审批或导出。

模型位置可能有误，分割分数不是准确率。服饰层级可以重叠；阴影不等于身体，
光效不等于第二件装备。后续控制仍须绑定明确的、实际核对过的部位。

## 模型与独立运行环境

“模型设置 → 各专家单独指定模型 → 角色结构解析”可选择支持图片的模型；
默认沿用规划模型和对应受保护 Key。解析模型与 SAM 分割是两个不同步骤。
修改设置不重算旧分析，旧结果保留其模型快照和调用回执。

维护者使用 Python 3.12 建立独立环境：

```powershell
npm run visual-structure:setup
npm run visual-structure:check
```

首次安装会下载固定版本 PyTorch、SAM 2 官方代码及 Tiny 权重，需要网络和磁盘空间。
默认 Windows/Linux 安装 CUDA 12.8 运行时；macOS 安装原生 PyTorch，支持 Apple
GPU（MPS）。`auto` 按 CUDA → MPS → CPU 选择，均以 FP32 推理。安装时可显式传
`-- --cpu`，将本机默认设备保存为 CPU。可通过
`FORGE_STRUCTURE_BOOTSTRAP_PYTHON` 指定 Python 3.12。安装不修改 SpritePipeline
现有环境，也不由查看页面或 GET 请求自动触发。

运行目录为忽略的 `work/visual-structure-runtime/`，来源及权重哈希在
`Tools/VisualStructure/runtime-profile.json`，通用依赖在同目录
`requirements.common.lock`。`FORGE_STRUCTURE_PYTHON` 和
`FORGE_STRUCTURE_WEIGHTS` 是服务端可选路径配置，不接受客户端任意路径。

设备策略保存在该运行目录的 `device.json`（例如 `{"device":"auto"}`）。服务进程的
`FORGE_STRUCTURE_DEVICE=auto|mps|cpu|cuda` 优先于本机配置，私有冻结作业中的 `device`
优先于环境变量。显式指定的设备不可用时任务报错，不静默改用 CPU、不自动重试。
可将本机配置改为 `{"device":"cpu"}` 后重新执行检查或提交本地纠正；已保存的语义
解析和旧结构版本仍可复用。设备不参与付费解析缓存身份，不改动模型来源与权重哈希。

`visual-structure:check` 会实际分配张量并执行设备运算。页面展示最近探测到的设备，
结果展示本次实际分割／追踪设备；旧记录缺失设备信息时不补造。单图和跨帧共用本地
推理锁，避免同时占用 GPU。MPS 追踪帧留在 CPU，采用分块注意力和连续布局池化，
分别控制注意力中间张量和修正固定 Torch 2.7.1 的池化布局偏差。运行结束后恢复适配。

回执记录 `requested_device`、`device`、`precision`、`torch`、`seconds`、
`attention_policy`、`pool_layout`、`mps_fallback_enabled`。耗时包括模型加载和本地推理，
不包括进程启动与外部语义调用。`mps_allocated_bytes` 与 `mps_driver_bytes` 是结束时
张量／Metal 驱动内存快照，不是峰值；CUDA 继续记录 `peak_gpu_bytes`。默认不打开
`PYTORCH_ENABLE_MPS_FALLBACK`；若用户启用，页面说明“已允许部分算子使用 CPU”，
这只表示允许回退，不表示已测得实际回退次数或比例。

可在独立运行环境中执行数值回归（无需模型、网络或付费调用）：

```sh
work/visual-structure-runtime/venv/bin/python -m unittest discover -s Tools/VisualStructure
```

Apple GPU 支持不等于所有请求更快，单图启动开销可能超过收益；硬件、部件数量、
序列长度都会影响速度和内存。跨设备蒙版仍需人工检查，不能把一致性当成分割准确率。

### Apple MPS 本机验收（2026-10-29）

M4 MacBook Air、10 核 GPU、16 GB 统一内存；Python 3.12、Torch 2.7.1、SAM 2.1
Tiny 固定权重，未启用 CPU 算子回退。使用固定框／点，语义与生成付费调用均为零。
下表为回执耗时（秒），每个请求独立启动 worker；单图为三次中位数：

| 样本 | CPU | MPS | CPU/MPS 蒙版差异 |
| --- | ---: | ---: | --- |
| 1024×1024 单图，1 部件 | 0.73 | 0.92 | 逐像素一致 |
| 64×64 单图，1 部件 | 0.72 | 0.93 | 逐像素一致 |
| 16 帧，1 部件 | 21.00 | 17.17 | 逐像素一致 |
| 32 帧压力测试 | 42.73 | 30.48 | 逐像素一致 |
| 64 帧压力测试 | 87.11 | 62.04 | 最多单帧 4 像素，最小 IoU 0.9747 |
| 16 帧含第 1／9 帧纠正及末帧未知标记 | 22.34 | 15.67 | 逐像素一致 |

32／64 帧由原 16 帧循环展开，用于内存与连续传播压力验证，不代表真实长动作精度。
64 帧结束时 Metal 驱动内存快照约 3.21 GB；该值不是统一内存峰值。检查了叠加预览、
所有冻结输入哈希和回执；长序列仅覆盖一个可见部件，未证明多部件／遮挡动作的质量。
另以隔离数据实测工作台调用 MPS、服务对象重建、切换 CPU 纠正、恢复 MPS 旧记录，
均复用原语义结果。数值回归覆盖分块注意力、完全遮罩、连续池化与异常后的适配清理。

## 持久记录与调用边界

`<SpritePipeline data_root>/visual-structures/<analysis-id>/` 保存不可变来源快照、
语义回执、部件蒙版、`revision-N.json` 和请求身份。它不是新的动画作品，也不增加
空动画任务。文件、源图、模型与解析器版本共同决定复用范围。

分析进程在付费提交前保存请求。相同来源/配置与重复请求复用原记录；失败或未知
调用也保留，换一个请求键不会暗中重新付费。进程停止后的不明调用需要核对，
不能通过刷新重发。若语义结果已保存而本地分割失败，结果继续可纠正，
本地重算不重复购买语义解析。

纠正带当前版本和 token。原图变化、旧版本写入、来源快照或蒙版被篡改会停止使用。
每次纠正清除此前确认，恢复也创建新版本。未改的区域按提示哈希复用，
修改记录与来源 PNG 始终分离。

## 本地接口

Web 通过既有受限代理访问以下 SpritePipeline API：

| 方法与路径（均以 `/v1/open-motion` 开头） | 作用 |
| --- | --- |
| `GET /structure-runtime` | 读取安装与语义模型配置状态 |
| `GET /references/{character_id}/structure` | 读取该原图的最新分析，无则返回空 |
| `POST /structures` | 明确授权一次分析；返回持久身份后后台执行 |
| `GET /structures/{id}` | 读取同一次分析；可指定 `revision` |
| `POST /structures/{id}/corrections` | 保存纠正、明确确认或恢复某个旧版本 |
| `GET /structures/{id}/source` | 读取该分析绑定的原始快照 |
| `GET /structures/{id}/masks/{part_id}` | 读取指定版本的真实部件蒙版 |

当前没有新注册的独立 MCP 结构工具。既有 `plan-motion` / `revise-motion` 的
`motionSpec.visual_structure` 可携带已核对分析的 `analysis_id` 和精确 `token`。
身份来自页面选择或已有 `get-motion` 的任务记录；不得猜测身份或默默重新解析。
不选择此字段的旧流程保持原契约。

## 已核对结构辅助制作（V3）

准备页的结构面板只增加“使用已核对的结构辅助本次制作”选项，默认关闭。
必须先核对并确认结构；确认本身不勾选该选项，也不调用绘图。切换角色清除选择。
规划与选帧调整仍分别使用原有预算，不增加隐式语义解析或目标图生成。

任务冻结原图哈希、结构版本、确认记录、可见部件蒙版尺寸及结构内容。外观与动作
专家仍独立查看原图；方案每段记录使用哪些可见部件、锚点和关系，以及对方案的
具体影响。相关约束编入原有 `motion.generation_hint`，随实际段级提示进入 PixelLab；
提交回执保存结构哈希和该段依据，能够核对“报告写了”与“绘图收到”是否一致。

未知或推断的位置不能成为确定控制条件。参考姿势坐标不应固定全段姿势，蒙版
中心不等于关节。当前 PixelLab 接口仍接收图片与文本，没有新增骨架、关节轨迹或
逐部件硬控制能力。现有真实首尾图片机制继续使用，不合成或替换生成端点。

结构改变、原图改变或冻结数据损坏会阻止新规划/后续绘图提交，已有帧与失败回执
保留。明确选帧修改继承该结构，但用户的本次修改要求优先；不扩张帧范围或改动
时长。查看、恢复和采用不会自动重新解析或另购一轮模型检查。

真实 A/B 必须固定输入、可用种子、模型和调用上限，检查完整动画及接缝。若两组
规划的分段、帧数不同，按整套规划效果报告，不能声称只隔离了某一句提示词。
先验证人工核对结构的控制价值，再决定是否值得扩大自动解析范围。

新建或明确修订的工作保存 `planning_format_version=3`，包含版本 2 的改进：策略专家使用只有 `proposal`
槽位的专用合同，最终 `plan` 只由协调专家发布。结构输入明确列出可用于引用的部件、
锚点和关系；不可见或推断信息单独作为不确定证据保留，不混入可选择的控制事实。
关系两端也必须有可见依据。原始结构记录不删除未知项，也不自动补成已知坐标。

缺少该字段的历史任务及版本 1、2 各自保留原提示、角色合同与结构视图。新建的选帧
修改任务冻结继承的结构视图版本，用户修改要求仍优先。无效响应停止并保存回执，
不截断总结、删除模型的未知字段、猜补方案或自动重新请求。

版本 3 对已验证的 TokenHub `kimi-k3.1-pro` 规划请求使用 `json_schema` 严格模式。
2026-10-27 的一次真实策略请求被受理并返回合规结果；原生适配器在同一冻结输入上
复现了完全一致的请求体，并重放通过已保存的解析结果。这个证据只覆盖该次兼容性，
不证明所有模型、所有任务或动画质量。其他型号、历史任务及现有视觉复核保持原方式；
请求失败不会自动降级或重发。

策略和协调的结构引用 Schema 按本任务已确认的可见标识生成枚举，不把未知标识
提供为可选控制事实；本地校验重复检查，服务忽略格式参数也不能绕过。这里只约束
原图事实引用，新的动作目标仍可由用户要求和专家建议形成，不把参考姿势固定不动。
内部通用对象补出的无意义空槽位仅从新任务的专家输入视图中省略，原始记录完整保留。

[腾讯云协议说明](https://cloud.tencent.com/document/product/1823/135872)列出了
`json_object` 和 `json_schema`。接入新模型时仍需单独验证实际支持，不以通用文档
或离线合同测试代替真实模型证据。

## 实际动画的结构观察

在完整动画或分段播放器下展开“结构观察”。默认只做本地追踪，不请求外部模型；
可明确勾选一次关键帧语义核对。此操作要求该动画所用的原图结构已确认，不能
用另一张原图、另一候选或旧版本的结构代替。已有分析会复用，刷新不会再次提交。

原始 PNG 是唯一播放来源，参考图只作上下文，不计入帧数和时长。部件区域按
实际帧追踪；语义锚点及关系只在已核对的关键帧出现，不插值成全段真实关节。
未知或遮挡区域不画确定位置，也不把原始预测的包围框、面积、主轴或重叠当作
专家可用坐标。原始预测仍保留供排查。区域扩张、缩小及重叠只提示查看，不能
直接判定装备丢失、重复动作、朝向改变或物理错误。

“纠正当前帧的观察”绑定正在查看的帧和部件，可添加保留/排除点，或标记未知、
遮挡。本地重算不重绘 PNG，也不追加语义请求。草稿按分析、版本、帧和部件保存；
来源过期时不能把草稿套到新动画。恢复创建新版本，已有版本和失败记录继续保留。

本地纠正初始化规则 `manual_first_frame_v2`：在实际动画第 1 帧明确纠正某个可见部件时，
该部件以本次纠正重新初始化，不再同时用旧参考区域牵引后续追踪。其他部件仍使用各自的
参考区域；自动语义提议、未知或遮挡标记、后续帧纠正不触发这项替代。新规则保留部件顺序，
从实际帧开始传播，参考上下文仍不计入播放。预测区域仍需逐帧核对，不承诺其他估计区域
逐像素不变，也不把单次纠正等同于全部帧已验证。

新分析冻结初始化规则，明确提交新的本地纠正会在新观察版本中保存当前规则。旧观察、
旧待恢复请求和旧复核保持原规则；读取或恢复不迁移、不新增语义调用。推理输入与回执的
规则不一致时拒绝使用。2026-10-28 的隔离 16 帧对照发现：保留错误参考区域时，首帧纠正
仅改善前 4 帧；替代旧初始化后，该样本头部区域持续贴近实际头部。此为观察工具的单样本
证据，不是生成动画质量或泛化验证，也不改变 V3 完整 A/B 的验收要求。

“用结构辅助专家复核”复用该组帧已保存的两次基础检查，最多新增两次独立意见
和一次争议复核。缺少基础检查的旧作品仍能追踪和纠正，但不能自动补跑收费基线。
这组意见另存，不更改原生动画状态、已有审批或导出；确认结构也不等于采用动画。
新分析版本或复核协议改变会使旧报告过期，恢复任务不会悄悄用新协议续费。

结构辅助争议复核保存判断依据的来源。明确用户要求必须引用冻结原话；规划建议
不能单独升级为用户要求。参考对象连续性及可见事件中断仍可构成真实问题。
规划细节偏差只可提示偏好或待核对；“未知”既不能证明对象消失，也不能证明对象
被正常遮挡。基础检查、模型原意见、来源校验及人工裁决分别保留。

时序记录保存在 `<data_root>/temporal-structures/<id>/`，包括精确帧快照、原图结构、
原始要求、单次模型回执、本地推理输入/结果、纠正版本与单独的复核账本。

新增本地接口均位于 `/v1/open-motion`，通过现有受限 Web 代理访问：

| 方法与路径 | 作用 |
| --- | --- |
| `GET /{work_id}/temporal` | 读取指定候选/阶段的最近分析，不生产任务 |
| `POST /{work_id}/temporal` | 绑定工作版本与原图结构，显式开始本地或一次语义分析 |
| `GET /temporal-structures/{id}` | 读取当前或指定结构版本与复核状态 |
| `POST /temporal-structures/{id}/corrections` | 保存帧内观察纠正、确认或恢复 |
| `POST /temporal-structures/{id}/review` | 显式授权最多三次附加视觉请求 |
| `GET /temporal-structures/{id}/frames/{index}` | 读取原始帧快照 |
| `GET /temporal-structures/{id}/frames/{index}/parts/{part_id}` | 读取指定版本的部件区域 |

## 验证范围

运行 Python `tests/test_visual_structures.py`，以及开放动作、壳层、lint、typecheck
和 build 检查。真实原图需查看全部部件叠加，并验证纠正、恢复、来源哈希和
调用次数。模拟掩码仅验证协议，不能证明低分辨率语义分割质量或跨角色泛化。

V2 增加 `test_structure_tracking.py`、`test_temporal_structures.py`、`test_tracking_review.py`
及原有生产视觉/评估回归。验收应实际播放整段和接缝，比较原像素、初始追踪与
纠正后区域，核对未知显示、刷新草稿、版本恢复、报告过期、旧任务和无重复调用。
人工关键帧纠正与自动解析结果分别统计；单角色开发样本不能证明组合泛化。

V3 增加 `test_structure_control.py`，检查旧序列化/方案哈希、冻结版本、真实绘图
输入、未知引用阻断、段间结构变更以及选帧修改保护。还需执行开放动作接口及
manifest 的 adapters/http/MCP 验证；模拟结果不计为真实质量改善。
