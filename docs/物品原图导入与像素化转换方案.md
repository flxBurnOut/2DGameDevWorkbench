# 物品原图导入与像素化转换方案

> 状态：方案，尚未实施；待裁决项已于 2026-11-16 裁决（见[第 7 节](#7-已裁决)）。核对基准为 `paper-vbyc` 提交 `d788574`，2026-11-16（UTC−05:00）。
> 来源：[交互物动画独立面板方案](交互物动画独立面板方案.md) 的待裁决项 D3。用户已确认两步都做，转换器做成独立打包、可单独调用的工具。

## 1. 结论

交互物动画的起点（对象原图）现在只能来自 PixelLab 生成的 128 px 物品原图。GPT Image 生成的物品图有两道障碍：

1. API 输出尺寸下限约 655,360 像素（约 810 × 810），不能直接生成 128 × 128，见 `lib/workbench/adapters/image-generation-size.mjs`。
2. 即使已有一张 128 × 128 透明 PNG，`reference-art import` 也只登记角色，物品移送只认 PixelLab 物品生成任务，见 `lib/workbench/adapters/reference-art.mjs` 与 `Tools/SpritePipeline/sprite_pipeline/prop_reference.py`。

本方案分两步解决：

- **第一步：导入 128 px 物品原图。** 任何合格的 128 × 128 透明 PNG 都可以登记为物品原图任务，经人工确认后移送为交互物动画对象，并记录来源。
- **第二步：像素化转换工具 PixelProp。** 把 GPT Image 物品图（或任意大图）确定性地转换成 128 px 像素风物品图。工具独立打包，可单独用命令行或 Python 调用，也接入工作台的任务、MCP 与网页。转换结果经第一步的同一条导入与确认路径进入动画流程。

不改变的规则：GPT Image 大图仍不能直接当参考；所有进入动画流程的原图都是 128 × 128、带透明背景、有登记来源与哈希；转换和导入不调用付费接口；PixelLab 动画生成的计费与授权不变。

## 2. 现状与改动点

| 位置 | 现状 | 改动 |
| --- | --- | --- |
| `reference-art` `import` | 只接受角色（`subject=prop` 直接报错） | 接受 `subject=prop`，尺寸固定 128 |
| `reference-art` `transfer` | 物品只认 `operation=generate`、模型 `pixflux`、有 `referenceJobId` 的任务 | 另接受物品 `import` 与 `convert-prop` 任务，需附人工确认 |
| `prop_reference.source_artifact` | 注释写明“网关从不接受上传的物品” | 按来源类型分别核验，新增 `provenance` 记录 |
| 交互物对象预设 | `object.json` 无来源字段 | 旁边增加 `provenance.json`，不改 `InteractablePreset` 模型和已有作品哈希 |
| 网页 | 交互物编辑器“获取图片”、交互物动画面板“还没有物品原图？” | 两处都增加“导入 PNG”和“从物品图转换” |

## 3. 第一步：导入 128 px 物品原图

### 3.1 接口

`reference-art` `import` 增加物品分支：

| 字段 | 规则 |
| --- | --- |
| `subject` | `prop` |
| `sourceImage` / `sourceImagePath` | 二选一，与角色导入相同（2 MB 以内 PNG，路径必须在仓库内） |
| `size` | 省略或 128 |
| `prompt` | 物品外观说明（与生成物品一致，最多 1800 字），作为对象的身份说明 |
| `name` | 可选显示名 |
| `facing`、`seed` | 不接受 |

校验与 PixelLab 物品原图相同：PNG、128 × 128、有可见像素、存在透明像素（`alpha` 最小值必须低于 255）。另外记录两项只读诊断，不阻断：半透明像素占比，以及颜色数。两项都偏高说明这不像像素画，网页上以提醒展示。

任务输出 `reference.png` 与 `result.json`：

```json
{ "subject": "prop", "model": null, "width": 128, "height": 128, "sha256": "…",
  "provenance": { "type": "import", "providerCalled": false, "sourceType": "browser-image",
                  "sourceSha256": "…", "diagnostics": { "semiTransparentPixels": 0, "colors": 23 } } }
```

### 3.2 移送与人工确认

`transfer` 对物品来源分三类核验：

| 来源任务 | 核验 | 是否要求确认 |
| --- | --- | --- |
| `generate`（PixelLab） | 保持现状：`pixflux`、`referenceJobId`、哈希 | 否 |
| `import` | 登记产物、哈希、尺寸与透明度；`provenance.type=import` | 是 |
| `convert-prop`（第二步） | 同上，并重算转换配方的输出哈希 | 是 |

需要确认的来源，`transfer` 输入增加 `confirmation: { note }`（至少 4 字），说明已核对视角、初始状态、部件完整、背景透明。缺少时拒绝移送，不会自动补上。确认可以由用户在网页填写，也可以由获得委托的 Agent 提交，规则见[第 7 节](#7-已裁决) P4。

对象 ID 沿用 `reference_<sha256(任务 ID) 前 24 位>`，重复移送复用同一对象。预设目录在 `object.json` 旁写入 `provenance.json`：

```json
{ "version": 1, "type": "convert-prop", "sourceTaskId": "…",
  "referenceSha256": "…", "confirmation": { "note": "…", "confirmedAt": "…" },
  "conversion": { "tool": "pixel-prop", "algorithmVersion": 1, "recipeSha256": "…", "sourceSha256": "…" } }
```

`type` 取 `import`、`convert-prop` 或 `pixellab`；`conversion` 只在转换来源时出现。已有的 PixelLab 移送对象没有这个文件，读取时按 `pixellab` 处理。

### 3.3 来源在下游可见

- 对象清单 `open-motion/references` 的每个交互物多带 `provenance`；交互物动画面板的对象下拉与对象条显示“PixelLab 生成 / 导入 / 转换”。
- 开放动作作品在规划时冻结对象来源：`work.character` 中加入 `provenance` 摘要（类型与哈希），已有作品不补写。
- 论文实验按来源筛选样本：转换或导入的原图不计入 PixelLab 物品原图的统计，除非实验明确要求。

### 3.4 网页

- 交互物编辑器“外观 → 获取图片”在“生成物品原图”旁增加“导入 128 px 物品原图”，交互物动画面板“还没有 128 px 物品原图？”增加同名页签。
- 流程：选择 PNG → 显示 1× 与 4× 放大预览和诊断提醒 → 填写外观说明 → 保存为导入任务 → 填写确认说明 → “用作交互物动画对象”。
- 尺寸不对时直接提示“请使用 128 × 128；大图可用‘从物品图转换’”，并带到第二步。

## 4. 第二步：像素化转换工具 PixelProp

### 4.1 打包形式

与 `Tools/SpritePipeline`、`Tools/VisualStructure` 并列，新建独立包：

```
Tools/PixelProp/
  pyproject.toml          # 包名 forge-pixel-prop，入口 pixel-prop；只依赖 Pillow（与 SpritePipeline 同版本区间）
  README.md / README.zh-CN.md
  pixel_prop/
    __init__.py           # convert(), inspect(), Recipe, ALGORITHM_VERSION
    recipe.py             # 参数模型、默认值、规范化与哈希
    pipeline.py           # 各处理步骤，纯函数
    quantize.py           # 确定性调色板
    report.py             # 报告与对比图
    cli.py                # 命令行
  tests/                  # 黄金样例、确定性、边界
  examples/               # 公开可提交的小样例与配方
```

安装方式：

- `npm run sprite-pipeline:setup` 把它以可编辑方式装进 SpritePipeline 的 `.venv`，服务和工作台直接调用。
- 单独使用：`pip install ./Tools/PixelProp`，或仓库内 `npm run pixel-prop -- <参数>`（脚本使用项目 venv 的 Python）。
- 不依赖工作台、网络和任何密钥；不读写用户数据目录，只处理传入的文件。

### 4.2 调用方式

**命令行**（标准输出为 JSON，便于 Agent 调用；退出码 0 成功、2 参数错误、3 输入不合格）：

```bash
pixel-prop convert input.png -o prop.png --size 128 --colors 24 --report report.json --compare compare.png
```

```bash
pixel-prop convert input.png -o prop.png --recipe recipe.json
```

```bash
pixel-prop inspect prop.png
```

**Python**：

```python
from pixel_prop import Recipe, convert
result = convert(source_bytes, Recipe(size=128, colors=24))
result.png        # 128×128 RGBA PNG 字节
result.report     # 参数、哈希、颜色数、透明度统计、警告
result.compare    # 并排对比图 PNG 字节
```

**工作台**：`reference-art` 新操作 `convert-prop`（见 4.5），以及不建任务的预览接口（见 4.6）。

### 4.3 配方（Recipe）与默认值

| 参数 | 默认 | 范围 | 作用 |
| --- | --- | --- | --- |
| `size` | 128 | 64 或 128（工作台物品固定 128） | 输出边长 |
| `padding` | 4 | 0–16 | 主体到画布边缘的最小留白 |
| `fit` | `contain` | `contain` | 裁到不透明包围盒后等比放入，不拉伸 |
| `anchor` | `bottom` | `bottom` / `center` | 主体在画布内的对齐方式；底对齐便于地面物件 |
| `resample` | `area` | `area` / `dominant` / `nearest` | 缩小方式，见 4.4 |
| `alphaThreshold` | 128 | 1–254 | 二值化透明度，去掉半透明边 |
| `colors` | 24 | 0 或 2–64 | 最多颜色数；0 表示不合并颜色，保留原有颜色 |
| `palette` | 无 | 文件路径、颜色列表或 `object:<对象 ID>` | 指定固定调色板；`object:` 取自已登记 PixelLab 物品原图的不透明颜色，默认不使用 |
| `dither` | `false` | 布尔 | 默认不抖动，保持平涂 |
| `removeIsolated` | `true` | 布尔 | 移除没有同色四邻的孤立像素 |
| `outline` | `none` | `none` / `dark` / 颜色 | 在主体外侧加 1 px 轮廓 |
| `background` | `alpha` | `alpha` / `key:#RRGGBB` | 源图没有透明背景时按指定色抠除 |

配方先规范化（补默认值、排序键），再计算 `recipeSha256`。同一张源图、同一配方、同一 `ALGORITHM_VERSION` 必须得到逐字节相同的 PNG：PNG 编码固定压缩级别，不写时间戳、ICC 或文本块。

### 4.4 处理步骤

1. **读取与校验**：只接受 PNG、WebP 或 JPEG，最长边不超过 4096，转为 RGBA。没有透明像素且未指定 `background` 时拒绝，提示设置抠色。
2. **裁切与放置**：按 `alpha > 0` 求包围盒，等比缩放到 `size − 2 × padding` 内，按 `anchor` 放置。
3. **缩小**：
   - `area`（默认）：在预乘 Alpha 空间按面积平均，避免透明边把颜色拉灰；
   - `dominant`：每个输出像素取对应源区域内出现最多的不透明颜色，边缘更硬，适合平涂插画；
   - `nearest`：取区域中心像素，只用于源图本身已是放大像素画的情况。
4. **透明二值化**：`alpha ≥ alphaThreshold` 设为 255，否则清为全透明（RGB 也清零）。
5. **调色板**：有 `palette` 时映射到最近色（按 OKLab 距离），否则对不透明像素做确定性中位切分，得到不超过 `colors` 种颜色再映射。实现保证固定遍历顺序，不依赖随机数。
6. **清理与轮廓**：可选移除孤立像素、加 1 px 外轮廓（轮廓不改变内部像素）。
7. **输出校验**：尺寸、有可见像素、存在透明像素；颜色数和半透明像素数写入报告。
8. **报告与对比图**：报告含源图哈希与尺寸、规范化配方及哈希、算法版本、输出哈希、颜色数、主体包围盒、警告（如主体过小、细线可能断裂）。对比图把源图缩到同高与输出 4× 最近邻放大并排，用于人工核对，不参与生成。

### 4.5 工作台任务：`reference-art` `convert-prop`

| 字段 | 规则 |
| --- | --- |
| `sourceTaskId` | 已完成的 `image-assets` 物品任务（`generate-prop` 或 `kind=prop` 的 `edit-image`），读取其登记的 `image.png` 并核对 `result.json` 哈希 |
| `sourceImagePath` / `sourceImage` | 或直接给文件；三者恰好一个 |
| `recipe` | 4.3 的配方，可省略取默认值 |
| `prompt`、`name` | 物品外观说明与显示名，同导入 |

执行在本机完成，不调用图片或 PixelLab 接口，不计费。输出 `reference.png`、`compare.png`、`recipe.json`、`report.json` 与 `result.json`（`subject=prop`，`provenance.type=convert-prop`，含源任务、源哈希、配方哈希、算法版本）。

移送时（第一步的 `transfer`）重新读取源图并按记录的配方重算，输出哈希不一致则拒绝，保证登记的转换可复现。源图或工具版本变化时，提示重新转换，不自动替换已移送对象。

执行位置：Node 适配器调用 SpritePipeline 服务新增的 `POST /v1/reference-art/convert-prop`，服务内导入 `pixel_prop`。这样网页、CLI、MCP 走同一实现；服务未启动时任务失败，并提示用 `npm run dev` 启动，不在 Node 侧另写一份算法。

### 4.6 网页：转换与调参

入口与第一步相同：交互物编辑器“获取图片”、交互物动画面板的物品原图卡片，以及 GPT Image 物品候选上的“转换为 128 px 物品原图”。

- 左侧选源：当前或历史 GPT Image 物品任务，或上传文件。
- 中间是对比：源图、转换结果 1×、4×，可切换棋盘格与深浅背景；颜色数、半透明像素数和警告显示在下方。
- 右侧调参：4.3 的主要参数，提供“平涂插画”“细线较多”“已是像素画”三个预设；“已是像素画”使用 `nearest` 且 `colors=0`。可选“沿用已有物品调色板”，从已登记的 PixelLab 物品中选择。
- 调参时调用 `POST /v1/reference-art/convert-prop/preview`，只返回预览图和报告，不建任务、不写文件；请求按配方哈希去抖与缓存。
- “保存转换结果”创建 `convert-prop` 任务；随后填写确认说明，再“用作交互物动画对象”。

### 4.7 Agent 与指导

- manifest 的 `reference-art` schema 增加 `convert-prop` 与物品 `import` 字段，`transfer` 增加 `confirmation`。
- 资产制作 Skill 路由增加：“只有 GPT Image 物品图 → `convert-prop` → 检查对比图 → `transfer`（附确认）→ 交互物动画”。
- motion 指南说明：转换或导入的原图可以进入动画流程，但 PixelLab 对这类参考图的动画效果未经验证；移送前须检查对比图并确认。用户已委托 Agent 检查时，Agent 查看对比图后可直接提交确认，说明写实际核对的内容；用户未委托或保留选择时，Agent 完成转换后停下，用 `workbench_present` 展示对比图，等用户确认。选源图和调参数属于常规选择，Agent 可自行处理。
- 独立使用的说明写在 `Tools/PixelProp/README*.md`。

## 6. 风险

- **画风不一致**：转换图是“缩小的插画”，不一定是干净的像素画；PixelLab 可能把它画回自己的风格，导致首段与原图不一致。对策是来源标记、对比图人工确认，以及先做小测再大量使用。
- **细节丢失**：8 倍缩小会断开细线、合并小部件，影响固定部件与运动部件的区分。报告给出“主体过小、细线可能断裂”警告；必要时先在 Aseprite 等工具修整，再走导入。
- **规则放宽的边界**：导入意味着任意 128 px PNG 都能成为动画起点。确认说明、来源文件和下游可见的来源标记用于追溯，但不能证明图片质量。
- **确定性依赖库版本**：Pillow 版本变化可能改变缩放结果。用 `ALGORITHM_VERSION` 与锁定的依赖区间约束；版本升级时更新黄金样例，并要求旧转换在移送前重算。

## 7. 已裁决

2026-11-16 由用户裁决，均采用方案建议。

| 编号 | 问题 | 结论 |
| --- | --- | --- |
| P1 | 默认颜色数 | 24；“已是像素画”预设不合并颜色（`colors=0`） |
| P2 | 是否提供“沿用已有 PixelLab 物品调色板” | 提供，作为可选参数（`palette: object:<对象 ID>`），默认关闭 |
| P3 | 导入与转换的物品是否允许 64 px | 不允许；交互物对象固定 128，工具本身支持 64 供角色或其他用途 |
| P4 | Agent 是否可以代替用户确认 | 仅在用户明确委托检查时可以，确认说明须写实际核对内容；与分段检查“用户已委托 Agent 检查时可直接裁决”的规则一致，不另加标记 |

P4 涉及的决定点：

| 决定 | 后果 | Agent 的做法 |
| --- | --- | --- |
| 选源图 | 选错可重做 | 用户指定时照做；有多张且未指定时询问 |
| 转换参数 | 本机处理，不计费，可重做 | 自行选择，属于常规选择 |
| 判断转换结果 | 不合格就回到调参 | 可以给出意见，结论并入移送确认 |
| 移送确认 | 之后所有动画都从这张图开始 | 已委托：查看对比图后提交确认；未委托或用户保留选择：停下展示对比图，等用户确认 |

移送确认本身不计费。之后的规划与 PixelLab 生成仍需各自的费用授权，不因确认而自动开始。
